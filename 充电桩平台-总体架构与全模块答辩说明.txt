东软电动汽车充电桩应用管理平台
总体架构与全模块答辩说明

使用说明
本文依据本次项目源码及已讨论的实现编写，不使用示例中的组号、姓名或完成比例。正文可用于介绍项目，按演示时长选读；文末提供12—14分钟的汇报安排。源码已有功能不等于全部通过运行验收，实际演示以虚拟机测试结果为准。

一、项目定位与需求分析

各位老师好，我们的项目是电动汽车充电桩应用管理平台。项目围绕用户充电、管理员运营管理和数据分析三个方面展开，目标是形成从查找电站、使用电桩、订单结算，到运营统计与负荷预测的完整软件业务流程。

需求分析首先区分了三类任务。用户需要知道哪里有可用设备、价格如何、如何控制充电以及如何查询费用；管理员需要维护站点、电桩、用户和订单，并处理异常与反馈；运营分析需要把业务记录转化为营收趋势、设备状态和负荷预测。

我们没有把需求仅仅列成页面清单，而是关注跨模块的一致性：用户开始充电后设备状态要变化，结束充电后订单、账户和电桩要一起更新，经营统计又要能反映结算结果。设计重点是让这些步骤能够衔接，而不是各页面独立展示互不相关的数据。

除功能需求外，还考虑了异常处理、权限校验、金额精度、重复请求、编辑内容保护和版本升级的数据保留。当前项目用于课程环境中的业务模拟与联调，没有接入真实充电硬件、车辆电池或正式支付系统。

二、总体架构与技术选型

1. 界面与部署关系

系统有Qt用户端、Qt管理端和Web数据大屏三个展示入口，但不是三个彼此独立的后端。用户端独立运行；管理端与业务服务器集成在同一个Qt程序中；Python分析程序读取同一业务数据库，将整理后的JSON交给网页展示。

完整数据流是：用户在Qt客户端发起操作，通过TCP发送JSON请求；服务端校验身份和参数，执行业务与数据库事务，返回JSON响应；客户端根据结果更新界面。管理员从管理界面调用相应业务功能。Python从数据库提取统计与负荷记录，调用模型并生成data.json；浏览器读取该文件，用ECharts绘图。

2. 技术分工

桌面开发使用C++和Qt 5。Qt Widgets负责窗口与控件，Qt Designer的.ui文件描述布局，QSS负责样式，.qrc负责公共资源，信号与槽连接事件和处理函数。Qt Network提供TCP通信，Qt SQL访问SQLite，Qt Charts支持管理端图表。

分析部分使用Python，SQLite查询与JSON处理完成数据整理，PyTorch负责神经网络训练与推理。网页使用HTML组织结构、CSS控制布局、JavaScript更新数据，ECharts绘制曲线、柱状图和环形图。

这套分工让C++承担桌面交互和核心业务，Python承担数据处理和模型计算。SQLite部署简单，适合当前虚拟机和局域网联调规模；未来如果访问量明显增长，需要评估独立数据库、服务拆分和后台任务队列。

3. 代码组织

client负责用户界面与网络请求；server负责管理界面、TCP接入、鉴权、业务规则和数据库操作；shared保存公共样式与资源；analytics包含数据生成、预测训练、采样和网页；scripts提供构建与检查；docs、database和config保存设计、迁移和规则说明。配置示例文件不应一概解释为已接入运行时的动态配置。

三、用户端模块

1. 登录与账户识别

当前以合法手机号作为用户入口，首次登录创建账户。客户端提交请求，服务端识别用户并返回账户与会话信息。账户状态决定是否允许后续操作。

设计理念是将身份与业务关联起来，使订单、月卡和反馈都归属具体用户。当前未接短信验证码，手机号格式正确不代表已经验证号码所有权；因此这是课程环境的账户入口，不应表述为生产级手机认证。

演示：输入手机号登录，展示个人账户和不同账号各自的订单记录。

2. 站点查询、电桩详情与导航

用户可以查询充电站，查看位置、地址、基础价格及站内电桩，进一步了解桩型、功率和空闲、在用、故障等状态。服务端统一提供数据，使用户端看到的设备与管理员维护的设备保持关联。

导航通过外部地图链接传递目的地位置，由浏览器打开地图服务。项目负责目的地信息和入口，不自行实现路线规划。外部网络、域名解析及地图服务状态都会影响导航可用性。

当前不能将本模块介绍成已经实现真实GPS定位、最优推荐算法或预约占桩；这些需要独立的功能和测试证据。

演示：选择站点、查看站内电桩、打开导航并核对目的地。

3. 充电控制与过程展示

用户选择空闲电桩后，可设置手动停止、按时长停止或按目标电量停止。服务端验证用户是否已有活动订单、账户是否满足条件以及电桩是否仍然可用，然后创建订单并更新状态。

客户端展示经过时间、估算电量和费用，服务端判断停止条件并最终结算。关键规则放在服务端，是为了避免页面关闭、客户端状态过时或多个客户端同时操作时产生不同结论。

电量由功率、时间及设定系数估算，尚未连接实际电表。达到目标电量的提示不等于车辆电池管理系统报告“充满”。本项目验证的是软件控制和结算流程。

演示：短时充电目标、手动结束以及订单状态变化。测试时同时观察用户余额和管理员看到的桩状态。

4. 订单记录

订单关联用户、电桩和业务时间，保存充电时长、电量、费用、支付、欠费以及自动停止原因等信息。用户查看自己的记录，管理员查看运营范围内的订单。

设计理念是让费用能够追溯：当前余额只是结果，订单及计费明细解释结果如何产生。异常结算不能简单隐藏，而要能够定位到具体订单与原因。

5. 个人信息与头像

用户可以查看和修改昵称、头像，并查看余额、欠费与信誉信息。头像涉及上传、存储、读取和显示，升级时需要连同相关数据目录保留。

界面需要区分服务器已保存的数据与用户尚未提交的编辑内容。后台刷新不应覆盖编辑草稿；保存成功后再同步已确认的数据。这部分此前出现过自动回滚问题，需要通过等待、切换页面、保存失败和再次登录等场景继续验证，不能仅凭“能保存一次”认定完全修复。

6. 余额与充值

账户记录可用余额，充值和消费改变钱包记录；欠费单独保存，避免用一个负余额字段同时表达多种含义。当前充值属于体验余额更新，没有微信、支付宝或银行的真实支付交易。

演示时可展示余额变化，但不能将按钮成功等同于真实支付成功。正式接入支付还需要交易单、回调验签、对账和退款等流程。

7. 月卡购买与使用

用户查看套餐、使用钱包购买并查询有效期和当日用量。新慢充卡为99元、每日60分钟；新快充卡为299元、每日10分钟，均有效30天，按桩型限制使用，高峰双倍消耗等效分钟。

每日额度不跨天累计，旨在形成稳定权益，避免大量累积额度集中释放。价格和额度曾因抵扣过高而调整；旧套餐下架，已购买用户保留原权益至到期。定价仅基于当前模拟功率与价格设计，不能据此宣称商业盈利。

8. 客服反馈

用户提交分类、标题与内容，查看工单和回复，并补充信息。管理员查看、回复和更新工单状态。反馈与用户绑定，形成可持续跟进的记录。

设计理念是保留问题处理过程，而不是用一次弹窗代替客服。设备问题可以通过反馈提交，但当前不能将它说成已实现独立报修派单、维修人员调度和维修闭环系统。

四、管理端模块

1. 管理员登录与权限

管理员使用账号密码登录。密码采用PBKDF2-SHA256、随机盐和迭代计算后保存哈希；页面不公开或预填管理员凭据。原默认演示口令仍需由部署者修改，隐藏提示不等于完成全部安全加固。

服务端区分普通用户与管理操作，不能仅根据客户端传来的“我是管理员”决定权限。用户数据访问需要结合实际身份检查。

2. 运营概览与业绩统计

管理端查看今日、本月、累计收入及订单等指标，并以图表呈现。统计结果由数据库查询得到，不在客户端独立维护另一套账。

设计中要区分订单应收金额、实际支付与欠费，避免把尚未收回的费用全部当成现金收入。答辩展示时应以当前查询口径解释数字，不能仅凭图表标题推断财务含义。

3. 充电站管理

管理员查看站点信息、新增站点并查看站内电桩明细。站点承载位置、地址与基础电价等信息，电桩通过站点关联组织。

拆分站点和电桩，是因为一个站点可以拥有多个不同类型、功率和状态的设备，不能把整个站点简单当成一台充电桩。新增数据写入数据库后，用户端重新查询即可获取。

4. 电桩管理与状态维护

管理员查询电桩状态并执行项目支持的远程重启操作；充电中的设备受到限制，不能随意改变状态而留下仍在计费的订单。

当前“重启”属于业务状态模拟，没有连接真实设备控制协议。功能边界是验证管理操作与订单状态之间的约束，不代表已向实体充电桩下发控制指令。

5. 用户管理

管理员按手机号或昵称检索用户，查看余额、欠费、信誉和账户状态，并进行冻结、解冻等管理操作。管理权限应服务于异常处理，不能绕开充电与结算约束随意修改数据。

6. 订单与结算查看

管理端查看订单及相关结算信息，帮助定位收费问题、异常停止和用户投诉。数据库视图将关联表整理成便于查询的业务结果，减少人工逐表拼接。

7. 客服、计费规则与月卡查看

客服区展示用户工单及回复，计费区展示时段规则、套餐和用户月卡用量。规则查看与任意编辑规则是不同能力；当前不能把展示表格一概描述为完整的在线配置后台。

8. 运行日志与审计

运行日志帮助观察监听、连接、请求和异常，审计记录用于追踪关键业务操作。数据库路径显示用于确认当前服务使用的数据文件，避免多个版本各读一份数据库导致结果不一致。

管理窗口打开不代表TCP监听成功。端口被旧进程占用时，新窗口可能仍可显示本地管理数据，但不能接收客户端连接。部署测试需要分别检查进程、端口和数据库路径。

五、服务端核心业务与一致性设计

1. TCP、JSON与请求关联

用户端使用QTcpSocket，服务端使用QTcpServer。JSON表达动作、参数和响应；请求编号帮助对应异步返回结果，会话信息用于识别身份。JSON只是业务格式，TCP是字节流，接收端仍需要按约定处理完整消息，不能假定一次读取就是一条请求。

2. 线程设计

网络监听在独立线程中运行，通过跨线程信号与槽传递事件。当前业务与数据库访问集中处理，以降低共享连接的复杂性。支持多个网络连接不等于每个客户端有一个独立数据库线程，也不等于已经通过高并发性能验证。

3. 事务与唯一约束

启动充电需检查设备与账户，同时创建订单和更新电桩。结束充电需更新订单、扣款或登记欠费、记录权益消耗并恢复桩状态。相关写入通过事务组织，成功后提交，失败则回滚。

活动订单唯一索引限制同一用户及同一电桩重复占用。应用检查负责正常业务提示，数据库约束作为最后一道一致性保障。条件更新并检查影响行数用于确认状态转换确实成功。

4. 金额与分时计费

核心金额使用“分”为单位的整数存储。订单跨越峰、平、谷时段时分段计算；月卡抵扣与时段倍率共同参与结算。计费快照与明细帮助解释已发生订单，降低后续规则变化影响历史解释的风险。

5. 信誉与欠费

信誉范围0—100，新注册用户初始10分，0分封禁，最低档无信用欠费额度。等级越高可获得不同额度；是否继续充电结合钱包、信用额度、已有欠费和当前费用判断，不能把信用额度当成真实钱包余额。

正常完成符合规则的订单增加少量信誉，欠费超过测试宽限时间后开始扣分。当前三分钟设置用于课程测试，不是商业运营参数。停止充电和偿还欠费是不同业务，余额不足不能导致订单无法结束。

6. 重复请求与输入安全

对相关写操作使用幂等机制，避免重复发送造成重复扣款或购卡；请求编号与幂等键的职责不同，前者关联响应，后者识别重复业务。参数绑定使用户输入作为数据执行；LIKE通配符还需处理字面匹配语义，通配符本身不等于SQL注入。

六、数据库与版本迁移

核心实体包括users、admins、stations、chargers、orders，以及会话、幂等记录、分时规则、月卡、每日用量、结算明细、反馈消息、日志和hourly_load等。新增持续采样还使用server_heartbeat、operational_load_samples、operational_load_hours。

主外键表达实体关系，非空、金额和唯一性约束表达业务底线。SQLite WAL模式支持读写协调，但并不使SQLite变成任意数量写事务可以同时执行的数据库。

当前新版运行数据位于/home/bit/ChargingData-v130/charging_platform.db。客户端不直接打开该文件，而是通过服务器访问；Python从同一文件读取统计。网页展示的是JSON快照，数据库变化后还需要生成程序更新它。

升级先停用旧程序，备份数据库及相关头像文件，再对副本进行迁移并验证。原账户、订单和密码保留，新注册信誉和新套餐执行新规则。Git用于共享源码，不应让队友通过共享文件夹同时写同一个SQLite文件；局域网测试应连接同一业务服务器。复制数据库也不是两份数据库自动双向同步。

七、Web展示与外部信息

网页以营收趋势、电桩状态、站点平均负荷和预测曲线组织信息。不同图形对应不同问题：折线看时间变化，柱图比较站点，环形图看状态构成。设备状态统计基于业务字段，不能当成真实设备心跳监测结果。

数据生成和页面显示分离，Python负责SQL与计算，JavaScript负责渲染。普通生成命令只生成一次；持续更新程序运行时每分钟重新生成，浏览器周期读取JSON。JSON通过临时文件替换发布，避免读取到写了一半的内容。

日历与显示时间使用Asia/Shanghai，周末标色不等于已识别所有法定节假日和调休。天气通过Open-Meteo查询，默认坐标为北京示例位置；交通需要配置有权限的高德Web服务Key。接口失败不生成虚构结果，Key不放入网页。图表库仍依赖外部CDN，断网时需区分页面数据故障与图表资源加载故障。

八、未来24小时负荷预测模块

1. 目标与实现

预测模块由Python和PyTorch实现教学版iTransformer，输入过去96小时的多站点负荷及小时周期、星期周期、周末特征，输出后续24小时各站负荷，再汇总展示。模型不是官方预训练权重，也不是营收预测或车辆满电预测。

2. 模型理念

iTransformer把不同变量的历史序列编码为变量token，注意力主要学习变量之间的关联。当前实现包括时间维度投影、2层Transformer编码器以及预测投影，并对每个输入窗口进行归一化与输出还原。它适合用于探索多站点关系，但是否更准确必须靠比较验证。

3. 训练与评估

20个epoch表示训练20轮，不是20层。按时间先后80%训练、20%验证，根据验证误差保存较好权重，输出MAE、RMSE以及昨日同期基线误差。验证集参与模型选择，因此还需独立测试集评估泛化；不能把演示数据指标当成真实运营预测能力。

4. 数据不足与历史模式

现有流程要求至少120小时完整连续站点记录，推理时取末尾96小时；训练还需验证区间和窗口数量，至少约9天，建议更多。缺数据不随意补零；若存在完整旧序列，显示带截止时间的历史预测。其时间范围从历史数据末端开始，不冒充从现在开始的未来24小时。

存在断档时选择最近满足要求的完整区间。新采样记录积累不足时继续使用旧区间，不能一启动采样就宣称实时预测恢复。未来时间异常则应检查系统时钟。

5. 持续采样

服务端每30秒写入数据库心跳；独立Python程序每分钟采样，只有心跳有效才记录。按在用电桩功率×0.85估算负荷，每小时需要60个不同分钟样本才汇总，缺失不回填，旧历史不覆盖。分钟样本保留7天，小时记录持续保存。

采样不是硬件遥测。心跳说明进程仍在处理事件，不保证TCP监听必然成功。采样进程、服务端和网页服务需要分别运行并检查。

6. 天气、交通与后续改进

技术详解增补：触发器、完整性、特殊设计及问题复盘

本增补以当前工作区源码为依据，是前文概述的细化与必要修正。特别注意：数据库触发器、定时器、信号槽、程序主动写日志是四种不同机制，不能混称为“触发器”。文中已实现指源码中有相应机制；是否通过本地验收另行说明。

十一、实际使用的三个数据库触发器

1. 用户金额同步触发器：sync_users_money_update

当前SQL如下，格式整理不改变逻辑：

CREATE TRIGGER IF NOT EXISTS sync_users_money_update
AFTER UPDATE OF balance_cents, debt_cents ON users
BEGIN
    UPDATE users
    SET balance = NEW.balance_cents / 100.0,
        debt = NEW.debt_cents / 100.0
    WHERE id = NEW.id;
END;

触发时机：执行涉及用户balance_cents或debt_cents列的UPDATE后。作用对象：刚刚被更新的那一行用户。NEW表示该行更新后的值。100.0用于按小数金额转换，避免整数除法截断。

设计背景：旧版使用REAL金额，新版将核心记账改成整数“分”，但旧字段还用于兼容部分历史查询。触发器使更新后的整数金额同步到旧字段，减少业务代码在每一条扣款、充值SQL中重复维护两套数值。

例如balance_cents更新为12345，触发后balance为123.45；debt_cents更新为678，debt为6.78。它不是“自动扣费”触发器，真正扣多少钱由业务计费代码决定。

2. 站点价格同步触发器：sync_stations_price_update

CREATE TRIGGER IF NOT EXISTS sync_stations_price_update
AFTER UPDATE OF price_cents ON stations
BEGIN
    UPDATE stations
    SET price = NEW.price_cents / 100.0
    WHERE id = NEW.id;
END;

用于维护站点基础电价的兼容字段。例如price_cents为138，对应price为1.38。它不负责区分峰谷时段，也不重算历史订单。

3. 订单金额同步触发器：sync_orders_money_update

CREATE TRIGGER IF NOT EXISTS sync_orders_money_update
AFTER UPDATE OF fee_cents, paid_amount_cents, outstanding_cents ON orders
BEGIN
    UPDATE orders
    SET fee = NEW.fee_cents / 100.0,
        paid_amount = NEW.paid_amount_cents / 100.0,
        outstanding = NEW.outstanding_cents / 100.0
    WHERE id = NEW.id;
END;

fee表示应付费用，paid_amount表示已支付，outstanding表示未支付部分。触发器只做字段同步，不负责判断是否允许欠费，不负责订单状态转换，也不自动释放电桩。

4. 三个触发器共同的边界

它们都是AFTER UPDATE触发器，没有使用BEFORE或INSTEAD OF，也没有INSERT、DELETE触发器。SQLite这里按受影响行执行；UPDATE即使将列设为原值，也可能触发，不应描述为“只有数值真的变化才触发”。

同步是单向的：整数分字段到旧REAL字段。手工只修改旧REAL字段不会反向更新整数字段。因此管理员不应通过随意编辑旧字段调整账目。INSERT也不会触发这三条规则，新记录需正确初始化相关字段。

触发器内部只更新旧金额列，不再更新列在触发条件中的分字段，避免这三个定义自身形成无限自触发链。它们在原语句事务内执行，不是异步后台任务。

同时保留两套金额属于版本兼容性冗余，不是理想的长期单一数据源设计。后续可统一使用整数列，并通过视图换算展示，逐步去掉冗余旧列。

演讲表达：我们没有把复杂计费写入触发器，而是让C++负责可测试的业务决策，让数据库触发器维护少量、明确的兼容字段关系。这样可以避免业务逻辑隐藏在数据库中难以追踪。

十二、完整性约束：实际有哪些，分别解决什么

1. 实体完整性：主键

admins、users、stations、chargers、orders，以及月卡、反馈、日志等主要表使用INTEGER PRIMARY KEY AUTOINCREMENT。主键识别记录，外键引用的是主键，不是可修改的昵称或站点展示名称。

sessions使用token TEXT PRIMARY KEY；幂等表仍有id主键并额外设置业务组合唯一约束。采样表采用(station_id,minute)复合主键，汇总登记表采用(station_id,hour)复合主键，避免同一时间重复登记。

SQLite具有类型亲和性，当前表没有声明STRICT。也不要套用其他数据库的全部主键细节：普通SQLite表的某些非INTEGER主键存在历史NULL行为，本项目token由程序生成且非空，但DDL没有显式给token写NOT NULL。若直接操作数据库，需要进一步补严这类约束。

2. 参照完整性：外键

实际关系包括：
- chargers.station_id引用stations.id，并设置ON DELETE CASCADE。
- orders.user_id引用users.id，orders.charger_id引用chargers.id。
- hourly_load.station_id引用stations.id。
- user_monthly_cards.user_id引用users.id，plan_id引用monthly_card_plans.id。
- daily_card_usage.card_id引用user_monthly_cards.id。
- order_card_details引用订单和用户月卡；order_tariff_details引用订单。
- feedback.user_id引用users.id。
- feedback_messages.feedback_id引用feedback.id，并设置ON DELETE CASCADE。
- credit_events.user_id引用users.id。

ON DELETE CASCADE表示删除父记录时相应子记录跟随删除，但不是“站点可以不受限制地删除所有业务”。例如电桩还被订单引用，其他外键仍可能阻止删除。没有显式级联的外键使用默认行为，不能宣称全部级联。

服务端打开连接时执行PRAGMA foreign_keys=ON。SQLite外键开关是连接级设置；用独立工具或脚本打开数据库，不应认为会继承Qt连接的设置。

边界：sessions.actor_id及反馈消息sender_id对应多种角色，当前没有普通单一外键直接约束；credit_events.order_id也没有声明订单外键；新增采样辅助表没有完整的站点外键。部分关联依靠程序保证，不应宣称“所有关联均有外键”。

3. 唯一性约束

管理员username、用户phone、电桩code、时段规则name和月卡套餐name具有唯一约束，避免重复身份或重复业务标识。

idempotency_keys对(actor_role,actor_id,action,idempotency_key)组合唯一。不同用户可有相同键值，但同一角色、用户和动作下同一业务键不能存成多条独立记录。

daily_card_usage对(card_id,usage_date)组合唯一，保证一张卡一天只有一个汇总用量记录。

credit_events对(user_id,event_date,event_type)组合唯一。因此某些信誉事件按“用户、日期、事件类型”限制重复记录，不能未经检查就说“用户刷多少笔订单都无限加分”。具体加分量和触发规则仍需结合业务代码解释。

4. 条件唯一索引：并发占桩的核心

CREATE UNIQUE INDEX IF NOT EXISTS uq_orders_active_user
ON orders(user_id)
WHERE status='charging';

CREATE UNIQUE INDEX IF NOT EXISTS uq_orders_active_charger
ON orders(charger_id)
WHERE status='charging';

这不是普通性能索引，而是带业务约束的部分唯一索引。仅进行中的订单参与唯一性判断；同一用户可以有多条已完成历史订单，同一电桩也可以先后被多个用户使用。

为什么不用UNIQUE(user_id,status)？因为那样还可能限制同一用户只有一条completed记录，误伤合法历史订单。部分唯一索引准确表达“只限制活动订单”的需求。

为什么不只用CHECK？跨行的“同一个用户有没有另一笔活动订单”不是简单的单行范围判断，使用唯一索引更合适。不能把它表述为已实现某条跨行CHECK。

5. NOT NULL非空约束

关键身份、订单用户和电桩、开始时间、核心金额等列不允许SQL NULL。自动停止原因auto_stop_reason设置TEXT NOT NULL DEFAULT ''，保证消费者可以按文本解释。

NOT NULL并不排除空字符串。电站名称TEXT NOT NULL不能单独阻止名称为''，还需要应用层验证或额外CHECK。

DEFAULT也不等于NULL替换：INSERT省略该列时可以取默认值；明确绑定NULL不会自动变成默认值；UPDATE赋NULL同样不会使用默认值。这是本项目手动停止订单报错的关键原因。

6. CHECK值域约束

金额：用户balance_cents、debt_cents非负，站点price_cents非负；订单base_price_cents、gross_fee_cents、fee_cents、paid_amount_cents、outstanding_cents、card_discount_cents非负。

目标：target_minutes>=0，target_energy_wh>=0。0用于表达未设置该类目标；具体最大值、模式和组合合法性由程序进一步检查。

角色：sessions.role只能为'user'或'admin'。

时段：start_minute在0—1439，end_minute在1—1440，multiplier_percent>0，card_multiplier>=1。

月卡：price_cents>=0，daily_minutes>0，valid_days>0。

每日用量：used_equivalent_minutes>=0。

这些CHECK并未覆盖所有业务。例如时段之间不重叠、完整覆盖一天、月卡用量不超过套餐额度、订单各金额之间的等式，不是当前DDL统一保证的内容。SQLite中CHECK表达式结果为NULL时也不等同于失败，关键列通常需要配合NOT NULL。

7. 应用层完整性，不要误称数据库约束

信誉分通过qBound限制0—100，并在迁移时做归一化，当前users.credit_score列没有CHECK(credit_score BETWEEN 0 AND 100)。手机号格式由正则验证，不是phone列自身的格式CHECK。

订单与设备状态合法性、目标模式、站点地址不能为空、反馈内容长度、账户冻结后的操作权限等主要由C++判断。charger.power、经纬度范围及若干状态字符串并没有完整的数据库值域约束。直接SQL操作可以绕过部分应用规则，这是后续需加强之处。

特别修正：当前最低档启动判断还检查首分钟应付费用minimumFee>0。因此，如果月卡完全抵扣首分钟，即使余额为零，也可能通过这一条判断。这与“最低档余额<=0无条件禁止一切充电”的最初文字要求并不完全一致。答辩应按当前实现说明，后续确认需求后再决定是否统一；本文不擅自改业务规则。

十三、视图、索引和数据库设计取舍

当前业务视图有四个：

v_user_accounts：将整数分换算为元，整理账户、状态、信誉和是否有头像。
v_order_settlements：整理订单目标、电量、原价、月卡抵扣、应付、实付、欠费与自动停止原因。
v_monthly_card_usage：关联已购卡、套餐与每日用量；LEFT JOIN让尚无用量的卡也能出现。
v_feedback_overview：关联用户和工单，并统计消息数。

视图是保存的查询定义，不是独立同步维护的第二份业务表。普通视图本身不提供完整的访问权限体系，SQLite文件的访问权限和应用权限仍很重要。这些视图没有配套INSTEAD OF触发器，不应说管理员通过视图就能任意写数据。

普通索引包括会话到期与撤销、用户反馈更新时间、审计日志创建时间等索引。它们用于改善相关查询访问路径，不等于所有查询都有最优索引。字段顺序与查询条件有关，后续可以用EXPLAIN QUERY PLAN评估，而不是仅凭建了索引就宣称性能提升百分比。

规范化方面，用户、站点、电桩、订单分别建表，月卡套餐与购买实例分开，反馈工单与多条消息分开，减少重复。订单保存启动时的价格、功率、桩型和时段JSON快照则属于有意保留的历史事实：站点后来改价，不应改变用户当时接受的计费依据。

快照不是无原则的数据冗余，但需要明确权威来源和生命周期。JSON时段快照也增加了查询和校验难度，不能宣称整个数据库每个字段都严格符合某个高级范式。

十四、解决问题的特殊方法：为什么这样实现

1. BEGIN IMMEDIATE、事务封装与RAII

DatabaseTransaction::begin()执行BEGIN IMMEDIATE。它在事务开始时尝试取得写事务资格，让写冲突尽早暴露，而不是先查出一组条件后在写入时才竞争。SQLite通常只有一个写事务能够进行；WAL不是无限并行写入。

事务对象记录是否active。作用域退出时，如果还未提交，就由析构函数尝试rollback，这是RAII思想：让资源生命周期帮助约束事务生命周期。commit失败时也会尝试回滚。

rollback失败会保存独立的rollbackError，便于区分原业务错误与回滚错误。但“记录失败”不等于“已自动恢复”：某些调用点没有完整处理返回值，析构函数不能把错误直接反馈给用户，代码也没有成熟的连接隔离、重建和人工恢复流程。因此只能说增强了失败可见性，不能说回滚绝不失败。

2. 条件更新并核对影响行数

UPDATE chargers SET status='in_use'
WHERE id=:id AND status='idle';

执行后检查numRowsAffected()==1。这使状态条件与更新在一个SQL动作中完成。若已经被占用，更新不到目标行，就不能继续假定自己占用成功。这不是CPU的CAS指令，但思想上同样强调“状态仍符合预期才转换”。它与事务及唯一索引共同工作，各自不能替代其他机制。

3. 状态机思维

电桩有空闲、在用、故障等状态，订单有进行中、结束或迁移取消等状态。一个操作是否合法取决于当前状态，而不只是按钮是否能点。例如充电中的桩不能普通重启；结束已经结算的订单不能重复扣款。正常状态与异常恢复都需要定义转换条件。

4. 整数记账与仍存在的舍入

余额以分保存，降低长期累计浮点误差；目标电量以Wh保存，展示时再换算kWh。但功率和电量估算仍使用浮点，单分钟费用也需要舍入，不能说整个计费链完全没有小数运算。

当前minuteFeeCents按每分钟估算电量乘电价倍率后四舍五入，并设置每分钟至少1分。因此“每分钟先舍入再累加”可能不同于“整单精确累加后舍入一次”，两种口径不能混用。低功率或零基础价的情况也值得专门测试；这些是计费规则选择，而不是整数存储自动解决的问题。

5. 幂等记录与请求编号

客户端对充值、开始/停止充电、购卡、更新资料、提交或补充反馈等操作生成UUID幂等键。服务端按角色、身份、动作和键查找既有响应，找到后返回缓存结果，并关联当前请求编号。

requestId用于异步响应对应；idempotencyKey用于同一业务重试识别，作用不同。

目前sendRequest每次未显式提供键都会生成新键，因此用户连续点击两次可能是两个不同键。它不自动等价于“防住所有双击”，还需要按钮防重、状态检查和数据库约束。

更重要的是，当前业务函数返回后才保存幂等响应，且保存结果没有完整传播。若业务已提交、进程在保存键前崩溃，重试仍有重复执行窗口。因此当前不能宣称严格exactly-once。后续应把幂等占位、业务写入和结果持久化纳入协调好的事务，并定义失败重试策略。

6. 身份绑定与越权防护

普通用户请求通过sessionToken查会话，服务端把实际actorId写入有效请求的userId，避免用户只改JSON里的userId就访问另一账户。管理员操作还需要角色校验。

当前本地trustedAdmin路径将操作者id视作1，扩展多管理员时审计归属需改进。用户手机号登录无验证码、TCP未加TLS、密码策略和登录限速不完善，因此密码哈希只能保护其中一层，不能被描述为端到端完整安全方案。

7. TCP消息分帧

TCP只保证字节流，不保证一次write对应一次read。客户端将紧凑JSON后加换行；接收端维护缓冲区，找到换行后取出完整一行解析，没有完整分隔就继续等待。多个完整消息到达时循环处理。JSON序列化会转义内容中的换行，区别于协议分隔符。

这解决正常的拆包、合包问题；同时还应考虑恶意超大消息、无换行导致缓冲增长、连接超时和背压。至少客户端当前缓冲读取没有明确展示完善的长度控制，不能说协议处理已覆盖所有攻击情形。

8. 编辑草稿保护与异步旧响应

m_profileDirty标记用户是否修改，m_profileSavePending表示保存中，m_profileSaveRequestId帮助比较请求先后。只有允许覆盖时才重填编辑字段；展示区的余额与信誉可以独立更新。

这比“输入框有焦点就不刷新”更全面，因为用户可能暂时切页但仍有未保存内容。还需测试保存前发出的旧查询晚于保存响应到达、保存失败恢复、退出重登等情况。当前有实现线索，但此前仍收到回滚反馈，不能直接宣称所有交互问题已消失。

9. 心跳、采样去重与完整小时

Qt心跳与Python采样分开：心跳证明服务端最近仍在运行；采样使用站点和分钟复合主键去重；满60个不同分钟才生成小时记录。停机缺数据不补零，这是对“未知”和“确实没有负荷”的区分。

边界：等间隔分钟快照的平均只是近似小时负荷，不是能量积分。连续写入新的采样数据不会自动填平旧断档；采样进程若延迟或中断，严格60样本条件可能使小时缺失。应根据实际运行优化调度，而不是隐藏缺口。

10. 原子发布与独立刷新周期

生成JSON先写临时文件，再替换正式文件，避免浏览器读到半个JSON。网页周期读取和后台周期生成分别存在；仅刷新浏览器不等于重新查询数据库。天气、交通调用频率单独控制，减少接口压力。

11. 模型数据时序与质量防护

训练按时间顺序划分，避免随机拆分让未来模式混入过去评价。归一化基于当前输入窗口，不拿预测目标统计量归一化。预测输入检查站点、负值、非有限值、重复小时和连续性。用昨日同期作为基线，可以判断复杂模型是否真的带来增益。

验证误差参与选权重，因此仍需要独立测试集；当前输出非负截断，但没有完整设备容量上限约束和不确定区间。历史展示避免时间造假，但不能代替真实负荷采集。

十五、项目中实际发生的问题与处理过程

以下区分“用户实际遇到”“代码审查发现”和“尚未证实根因”，避免把建议当成已完成修复。

事件1：Qt相关包无法安装
现象：dpkg选项和SQLite插件包名输入错误，随后遇到未满足依赖；Thunderbird的snap安装步骤还曾停留较久。
处理：区分字母l与数字1、修正包名，处理包管理依赖与网络问题。此类问题属于开发环境，不是项目SQL语句错误。
边界：不要为了安装依赖删除包管理锁文件或随意中断系统升级；Python虚拟环境安装和apt系统安装也不同。

事件2：地图和外部网页无法打开
现象：浏览器提示找不到站点，域名查询无结果，ping公网IP和192.168.83.2网关均失败。
排查：先看ip route，再测网关、公网IP和域名，逐层区分本地链路、外网和DNS。
处理：检查Windows的VMware NAT/DHCP服务，断开重连ens33；用户随后得到网关0%丢包的结果。
边界：网关恢复不单独证明导航坐标正确，还需测试外网与最终目的地。

事件3：启动文件不存在、多个版本混用
现象：指定ChargingUpgrade-v130目录不存在，find找到旧目录和回收站中的程序。
原因：尚未把新版压缩包解压到指定目录，或在错误工作目录执行相对路径。
处理：确认压缩包、解压、cat VERSION、重新构建，依据find结果运行build/bin程序。
经验：源码版本、编译产物、运行进程和数据库路径是四个不同对象，必须分别确认。

事件4：编译出现unused变量与函数警告
现象：currentFee、chargingFee未使用，但最终输出Build completed并生成程序。
处理：区分warning与error，先确认链接成功。未使用代码应后续清理，不能把警告解释为数据库损坏，也不能据此宣称功能已全部通过。

事件5：服务状态未监听
现象：管理端界面存在但TCP状态未监听。
排查方案：使用ss查看9999端口、pgrep检查多个服务端、查看启动失败日志。
状态：此前没有完整日志证实最终根因，端口冲突是可能原因，不能写成已经证明并修复。

事件6：网页启动报Address already in use
现象：Python http.server绑定8080失败。
原因：8080已经被其他进程占用。
处理：使用8081访问当前目录，或确认占用进程后关闭旧网页服务。换端口不需要修改数据库或重新训练模型。

事件7：修改资料几秒后恢复旧值、充电时自动跳页
原因方向：后台定时响应更新了可编辑控件，或刷新时重新选择了充电页面。
处理设计：编辑草稿标记、保存状态、请求顺序判断，数据刷新与导航行为分离。
状态：用户曾报告修复后仍有回滚现象，尚需排除旧程序及补充竞态复测，不能仅以源码含标记认定彻底解决。

事件8：收到登录请求却未进入系统、qintptr警告
现象：服务端收到多条login_user，随后出现Cannot queue arguments of type qintptr。
处理：注册qintptr元类型，配合跨线程信号槽传递。
状态：用户后来确认登录成功，但现有记录不足以证明早期所有登录等待都由同一原因造成。

事件9：手动停止订单失败
现象：NOT NULL constraint failed: orders.auto_stop_reason。
根因：QString()可能绑定为SQL NULL，非空字段拒绝写入；DEFAULT ''不能替代显式NULL。
修复：SQL使用auto_stop_reason=COALESCE(:reason,'')；源码绑定也改用非空QStringLiteral("")作为手动停止默认值。
验证：空值、空字符串、自动停止原因的SQL写入检查通过。实际订单结算仍以虚拟机复测为准。不要通过删除非空约束掩盖错误，也不要清空数据库重建订单。

事件10：余额不足时订单无法收尾的设计风险
处理思路：停止和结算不以“必须足额付款”作为唯一前提；可用余额用于支付，剩余进入欠费，再根据账户和信誉限制后续使用。
验证重点：防止重复结算、账户金额与订单欠费不一致、扣分重复以及有月卡时零余额的例外。这不是简单添加CHECK(balance>=0)就能解决的业务问题。

事件11：月卡一天可能回本
原因：原套餐卡费与快充功率、每日抵扣时长不匹配。
处理：调整新套餐价格、时长和桩型限制，旧套餐停止新购，保留既有卡权益。
边界：回本周期取决于实际站价、时段、功率与用量，不能固定声称所有用户都在第13天回本，也不能把售价合理等同于已经验证经营利润。

事件12：Python虚拟环境创建失败
现象：ensurepip不可用。
处理：安装与Python版本匹配的python3.12-venv，再创建项目虚拟环境。无需删除业务数据库。

事件13：PyTorch依赖下载过大
现象：torch安装后继续下载CUDA、cuDNN等大文件。
原因：安装来源选中了带显卡依赖的发行包，而当前模型代码仍在CPU上运行。
处理选择：下载阶段可取消并选择CPU发行包；用户最终选择继续安装。文件在Ubuntu虚拟环境和缓存中，也占用Windows承载的虚拟磁盘空间，但不会给Windows安装显卡驱动。

事件14：模型存在却暂无可用预测
证据：当时北京时间19:07，最新历史记录14:53，已超出两小时阈值；旧程序还先归整点，使显示的时间差进一步扩大。
根因：已有训练与过期检查，却缺少持续采样和历史展示衔接，不是重新安装依赖可以解决的问题。
修复：新增带日期的历史预测、服务心跳、分钟采样、完整小时汇总和周期JSON生成；断档时选择满足要求的历史连续区间。
验证：采样去重、完整小时、失效心跳与断档选择自动检查通过。补丁没有通过伪造日期让曲线看起来新鲜，也没有声称已经完成真实电表采集。

事件15：图表文字倾斜
原因：ECharts横轴标签配置rotate:25，是防重叠的布局选择。
处理：按用户偏好改为rotate:0，并强制刷新浏览器。站名过长时还需要考虑换行、缩写或宽度，不应只旋转角度就认为所有屏幕适配完成。

事件16：更新版本与保留数据
处理：保留原数据库备份，新版使用ChargingData-v130副本，头像文件一并保留，分析程序显式指向同一副本。
必须修正的说法：迁移并非“所有记录状态完全不变”。当前会把同一用户或电桩的冲突活动订单中部分记录改成cancelled_migration，再建立唯一索引，并根据剩余活动订单修正桩状态。
风险：这一历史冲突处理没有完整演示财务对账；迁移也没有整体版本事务包住所有步骤。旧列只在缺失时补加，已有列的DEFAULT、CHECK不会因为CREATE TABLE IF NOT EXISTS自动变成新定义。答辩要说“备份后迁移并验证”，不能说无条件无损升级。

十六、可在答辩现场只读展示的数据库检查

以下命令在Ubuntu中执行，读取实际数据库对象，不修改业务数据：

python3 - <<'PY'
from pathlib import Path
import sqlite3
p = Path.home() / 'ChargingData-v130/charging_platform.db'
with sqlite3.connect(p.as_uri() + '?mode=ro', uri=True) as db:
    for name, sql in db.execute("SELECT name,sql FROM sqlite_master WHERE type='trigger' ORDER BY name"):
        print('\n触发器：', name, '\n', sql)
    for name, sql in db.execute("SELECT name,sql FROM sqlite_master WHERE type='index' AND sql IS NOT NULL ORDER BY name"):
        print('\n索引：', name, '\n', sql)
    print('\nusers列结构：')
    for row in db.execute('PRAGMA table_info(users)'):
        print(row)
    print('\norders外键：')
    for row in db.execute('PRAGMA foreign_key_list(orders)'):
        print(row)
    print('\n外键违规：', list(db.execute('PRAGMA foreign_key_check')))
PY

读出的结果才是该虚拟机数据库当前实际状态；源码声明代表目标，不保证每一个旧库结构都已经完全一致。外键检查为空也不代表全部业务规则正确，它无法检查未声明的关系和应用规则。

不要在正在使用的数据库上为了演示约束而故意插入冲突订单。约束破坏测试应使用临时内存库或备份副本；已有scripts/static_database_test.py就是从源码提取DDL，在隔离数据库中验证相关结构、金额和活动订单唯一性。

十七、老师可能追问的深入回答

问：你们为什么既有应用检查又有数据库约束？
答：应用检查提供业务语义和友好提示，数据库约束拦截最终非法状态。两个请求可在检查之后竞争，所以不能只靠前端或单次查询判断。

问：触发器是不是会自动完成整笔结算？
答：不会。现有三个触发器只同步兼容金额列。结算由C++计算并使用事务提交，职责明确。

问：事务是否等于线程锁？
答：不是。线程锁协调进程中的执行，数据库事务管理持久数据的原子提交和并发访问；本项目用BEGIN IMMEDIATE及数据库约束，并通过Qt线程分工减少连接共享风险。

问：为什么不用触发器扣信誉？
答：扣信誉涉及经过时间、欠费政策和账户状态，当前由定时业务逻辑处理。数据库触发器由数据操作触发，不会因为时间过去三分钟自动执行。

问：为什么不让数据库余额为负？
答：把可用余额与欠费分开，使支付能力与债务含义清晰。非负约束只是底线，欠费产生、信用额度和停止条件还需业务逻辑协调。

问：是否完全防住重复支付？
答：已有幂等键与状态检查，但幂等结果保存与业务提交仍有崩溃窗口，尚不能宣称严格一次执行。正式支付还需要外部交易号、回调验证与对账。

问：为什么历史预测仍有价值？
答：可以验证模型加载、输入输出和展示链路，并回看某个历史时点之后的预测。但它不是当前调度依据，必须明确日期，不将过期数据重新标注为今天。

问：数据量少是否自动改用别的算法？
答：当前没有这样的自动降级实现。合格旧序列可以历史展示，没有合格数据则不可预测。后续可以设计基线回退，但必须独立标明算法和适用条件。

问：项目最大的经验是什么？
答：界面能够运行不等于系统正确。需要同时确认消息顺序、业务状态、数据库约束、运行进程和数据时间。很多实际问题发生在模块交界处，例如Qt空字符串到SQL NULL、旧源码到新运行程序、业务数据库到网页快照，以及训练完成到当前预测之间。
